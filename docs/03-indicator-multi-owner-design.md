# インジケーター配信：複数オーナー・複数PC構成の設計メモ

作成日: 2026-08-16

## このメモの位置づけ

**実装コードは未発見の状態で書いている。** 設計上の一般論としては成立するが、実際のコードと突き合わせた検証はできていない。
コードの所在が判明したら「4. 実装の所在を特定する手順」を実行し、そのうえで本メモの内容を実装と照合すること。

前提として置いた読み: オーナーが売買シグナル等を送信し、購読者側のインジケーターが受信して動く配信型の構成。
オーナーが複数人おり、それぞれ複数台のPCから操作する。この前提が違う場合、以下の結論も変わる。

---

## 1. 結論

**オーナー機にも受信を入れるのは正しい。ただし目的は「シグナルの実行」ではなく「状態の可視化と到達確認」。**

この切り分けを曖昧にしたまま送受信の両方を入れると、後述のエコーループを踏む。

---

## 2. 複数オーナー × 複数PC で必ず出る問題

| # | 問題 | 起きること |
|---|---|---|
| 1 | 二重送信 | オーナーAとBが同じ相場を見て同時にエントリーを送る。購読者は2ポジション持たされる |
| 2 | 順序の逆転 | PC AのENTRYとPC BのCLOSEが、遅延でCLOSE→ENTRYの順に届く。決済したはずが建ったまま残る |
| 3 | エコーループ | オーナー機に受信も入れると、自分の送信を自分で受け取って実行し、また送信する |
| 4 | 状態の分岐 | 「現在のポジション状況」を各PCローカルに持つと必ずズレる。ズレた状態を元に次の判断をするので事故が育つ |
| 5 | 追跡不能 | 誰がいつどのPCから送ったか残らない。誤送信の原因究明ができない |
| 6 | 認証の使い回し | オーナーアカウント1つを全PCで共有すると、1台トラブっても全体失効しか手がない |
| 7 | 復帰時の暴発 | 落ちていた間に溜まったシグナルを復帰時にまとめて実行。数時間前のエントリーが今発火する |

---

## 3. 推奨する設計

### 3.1 サーバー（共有ストア）を唯一の真実にする

PC同士を直接同期させない。オーナー機はどれも「サーバーに送る」「サーバーから読む」だけにする。
これで問題4が消え、問題2の大半も消える。

### 3.2 シグナルが持つべき最低限のフィールド

| フィールド | 目的 | 対策する問題 |
|---|---|---|
| `signal_id` | 冪等キー。受信側は既知IDを捨てる | 1, 再送 |
| `seq` | 単調増加の通し番号。自分が見た番号より古いものは捨てる | 2 |
| `origin` | `owner_id` + `device_id` の両方。片方だけでは足りない | 3, 5 |
| `expires_at` | 有効期限。切れていたら実行しない | 7 |

### 3.3 オーナー用インジケーターは「送信 + 受信（表示専用）」

- 受信側で `origin` が自分発だったら**実行対象から外し**、「配信された」という到達確認としてのみ表示する → 問題3が消える
- 他オーナー発のものも実行せず状況表示にとどめる → 「Bが既に送っている」のが見えるので問題1を運用で防げる

### 3.4 送信権限を絞る

一番堅いのは「同時にアクティブな送信端末は1台だけ」というロック（リーダー）方式。
全員がいつでも送れる形にするなら、二重送信の自動排除（同一銘柄・同方向で一定時間内は後発を弾く等）が必須。

### 3.5 配布物は1本にしてモード切替

ファイルを送信用・受信用に分けると版ズレが起きる。1本にまとめてモード切替が運用は楽。
ただし**デフォルトは受信のみ・送信は明示的にON**にすること。そうしないと設定ミスで購読者機から誤配信が飛ぶ。

### 3.6 端末ごとの個別トークンと監査ログ

端末ごとにトークンを発行し、`owner_id` / `device_id` / 時刻 / 内容 を監査ログに残す。問題5と6はこれで片付く。

## 4. 実装の所在を特定する手順（Mac側で実行）

### 4.1 背景

2026-08-16 時点で、以下をすべて確認したが実装コードが見つからなかった。

- `kirin-cyber/anime` の全 git 履歴 → 調査レポート2本と README のみ。インジケーター関連は皆無
- アカウントがアクセスできる全14リポジトリの一覧 → 名前がインジケーターに該当するものなし
- クラウドセッション履歴15件 → インジケーター関連は本セッションのみ

本セッションが `anime` を参照しているのは、直前の「記事読み上げ調査」セッションのブランチを起点に引き継がれたためで、
ここに実装がある根拠ではない。デスクトップのローカルセッションはクラウド側の一覧には出てこないため、
Mac上で開発していた場合は上記の調査では原理的に見つからない。

同種の事象が過去にも発生している（2026-06-10 のセッションが「ゲームのコードが見つからない、未pushの可能性」で停止）。

### 4.2 Macの Claude Code に貼るプロンプト

```
このMacの中から、「インジケーター」の送信/受信機能を開発していたプロジェクトを探して、
見つかったものすべてについて以下を報告してください。

1. プロジェクトの絶対パス
2. git remote -v の出力（remoteが無い場合は「remoteなし」と明記）
3. 現在のブランチ名
4. 未コミットの変更の有無、および未pushのコミット数
5. 主要なソースファイルの一覧（拡張子と行数）
6. 送信側・受信側がどう分かれているか（ファイル構成から読み取れる範囲で）

探索のヒント:
- ホーム配下の .git ディレクトリを持つフォルダを総当たりする
- MT4/MT5 の可能性があるなら
  ~/Library/Application Support/MetaQuotes/Terminal/*/MQL4|MQL5/Indicators 配下も見る
- *.mq4 *.mq5 *.ex4 *.ex5 が無いかも確認する
- ソース内に「シグナル」「送信」「受信」「owner」「signal」を含むものを探す

見つからなかった場合は「見つからなかった」と明言してください。推測で埋めないこと。
```

### 4.3 ターミナルに直接貼る場合

```bash
# (1) ホーム配下のgitリポジトリとそのremoteを一覧
find ~ -maxdepth 6 -type d -name .git 2>/dev/null | while read -r g; do
  d=$(dirname "$g")
  echo "=== $d"
  git -C "$d" remote -v | head -2
  git -C "$d" log -1 --format='  last: %ad  %s' --date=short 2>/dev/null
done

# (2) MT4/MT5 のインジケーターフォルダ
ls -d ~/Library/Application\ Support/MetaQuotes/Terminal/*/MQL[45]/Indicators 2>/dev/null

# (3) MQL のソース/バイナリ
find ~ \( -name '*.mq4' -o -name '*.mq5' -o -name '*.ex4' -o -name '*.ex5' \) 2>/dev/null | head -40

# (4) 中身から探す
grep -rl -E 'signal|シグナル|インジケーター' ~ \
  --include='*.mq4' --include='*.mq5' --include='*.py' \
  --include='*.js' --include='*.ts' 2>/dev/null | head -40
```

### 4.4 判定

- **(1) で remote が出た** → そのリポジトリ名を教えてもらえれば `add_repo` で接続し、実装と本メモを照合する
- **remote が無い / 何も出ない** → 未push。GitHubに上げるところから始める必要がある

## 5. 運用上の申し送り

リポジトリ名と中身が一致していない状態が既に発生している（`anime` リポジトリの中身はTTS市場調査とWeb小説調査）。
スマホから新規セッションを始めると直前のセッションのリポジトリが引き継がれるため、
**セッション開始時に対象リポジトリを明示的に選ぶ**か、プロジェクトごとに名前の一致したリポジトリを用意しないと、
今回と同じ「どこにあるか分からない」が繰り返される。
